#### A-2a · P0 · B — Cualquier usuario puede editar y **borrar** el perfil de cualquier otro

- **Dónde:** `public.profiles` — políticas `auth read profiles [SELECT] USING true` y
  `auth write profiles [ALL] USING true` (`pg_policies`).
- **Medido**, como *Alberto Garza* (sales, sin admin en nada), con rollback:

  | Prueba | Resultado |
  |---|---|
  | `role → admin` (propio) | bloqueado por `guard_role_change` ✓ |
  | `timetracker_role / recruiting_role / module_access` (propio) | bloqueados por los guards ✓ |
  | **`permissions` (capacidades extra, propio)** | **PERMITIDO** |
  | **`store` (propio)** | **PERMITIDO** |
  | **`full_name` / `username` de OTRA persona** | **PERMITIDO** |
  | **`DELETE` del perfil de OTRA persona** | **PERMITIDO (1 fila)** |

- **Por qué importa:** los guards protegen las columnas de rol y acceso, pero **no la fila**.
  Borrar un perfil dispara **27 FKs `ON DELETE CASCADE`** (`pg_constraint`): se van
  `clockin.time_entries`, `timetracker.sessions`, `timetracker.payrolls`, `screenshots`,
  `driver_shifts`, `employee_files`… — el historial de horas y nómina de esa persona,
  borrado por cualquier compañero con la clave anónima y su propia sesión. Cambiar el
  `username` ajeno es cambiarle la puerta de entrada.
- **Fix:** partir la política: SELECT como está (o ver A-2g); UPDATE `USING (id = auth.uid() OR current_user_role() = 'admin')`; DELETE solo admin; y un trigger que trate `permissions`, `store` y `username` como ya se tratan `role` y `module_access`.
- **Riesgo:** que alguna pantalla escriba perfiles ajenos sin ser admin. `grep .from("profiles").update`: 24 sitios, todos o propios o desde el diálogo de Usuarios (admin) o desde acciones con service role. Verificar antes de aplicar.
- **Contradice:** nada. D-053/D-057 separaron las columnas; dieron por hecho que solo la app escribía.

#### A-2b · P0 · B — Un chofer puede editar los Ajustes de la empresa

- **Dónde:** `public.settings` — `auth write settings [ALL] USING has_deliveries_access()`.
- **Medido**, como *Maximo Garza* (driver), rollback: `UPDATE settings SET same_day_surcharge=999` → **PERMITIDO**; `UPDATE settings SET stores='[]'` → **PERMITIDO** (deja la empresa sin tiendas).
- **Fix:** escritura solo `current_user_role() = 'admin'` (o admin + capacidad `settings`).
- **Riesgo:** bajo — la pantalla de Ajustes ya es solo admin en la UI.

#### A-2c · P0 · B — Un chofer puede borrar el historial de órdenes

- **Dónde:** `public.order_events` — `auth write order_events [ALL] USING has_deliveries_access()`.
- **Medido:** `DELETE FROM order_events` como chofer → **PERMITIDO (935 filas)**. Es el registro de auditoría de cada orden (quién aprobó, quién entregó).
- **Fix:** INSERT para miembros; **sin UPDATE ni DELETE** para nadie (o solo admin). Mismo criterio que `security_events`, que ya lo hace bien.

#### A-2d · P0 · B — El coste del ERP se lee saltándose la vista que lo enmascara

- **Dónde:** `erp.products.cost` — grant de columna `authenticated: SELECT` (`information_schema.column_privileges`) + política `products read [SELECT] USING (record_status='published' OR mgr/admin)`.
- **Medido**, como un vendedor con acceso al ERP (rollback):

  ```
  select cost from erp.products where cost is not null   →  LEE 6,104 filas (ej. cost=10.08)
  select cost from erp.app_products (la vista)            →  0 filas con coste
  erp.can_see_cost()                                      →  false
  ```

- **Por qué importa:** la garantía "el coste nunca llega a una sesión que no es admin/manager,
  aplicada en la base" (decisión #29 del ERP original, y el incidente documentado allí de un
  guard que falló abierto) se mantiene **solo en la vista**. La tabla debajo está expuesta a
  PostgREST con `Accept-Profile: erp`.
- **Fix:** `REVOKE SELECT (cost) ON erp.products FROM authenticated` — RLS no oculta columnas,
  los grants de columna sí. Antes, confirmar que ningún cliente de navegador lee `cost` de
  `erp.products` directamente (los lectores con service role no se ven afectados).
- **Riesgo:** medio — un `select("*")` desde el navegador sobre `erp.products` empezaría a fallar. `grep`: las lecturas de catálogo van por `app_products` (`lib/erp/actions.ts:34-35`).

#### A-2e · P1 · B — En HR, un reclutador escribe lo mismo que un admin

- **Dónde:** 11 tablas de `recruiting.*` con `recruiting write X [ALL] USING has_recruiting_access()` — incluidas `settings`, `stages`, `questions`, `question_sets`, `templates`, `custom_fields`.
- **Qué:** el escalafón admin/manager/recruiter existe (`current_recruiting_role()`) pero solo lo usan `employee_files`/`employee_docs` (094). Un reclutador puede borrar etapas, reescribir preguntas o vaciar candidatos.
- **Fix:** escritura de configuración (settings/stages/questions/templates/custom_fields) → admin/manager; candidatos/contactos/adjuntos → cualquier miembro.
- **Contradice:** D-057 dice que HR "no tiene permisos finos, solo el escalafón" — esto no añade permisos finos, usa el escalafón que ya hay.

#### A-3 · P1 · B — Auto-concesión de capacidades de Deliveries

- **Dónde:** columna `profiles.permissions` (lo que `extraCaps()`/`hasCap()` leen — `constants.ts:686-692`; capacidades: create, approve, fulfill, deliver, dashboard, settings, route_plan).
